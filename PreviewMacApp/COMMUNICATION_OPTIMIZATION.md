# PreviewMacApp 通信优化方案

## 当前问题分析

### 1. 轮询延迟高
- **Mac 端**: 定时器每 10ms 轮询一次 `callNative` 请求
- **JVM 端**: 需要轮询 `callKotlinMethod` 和 `callNativeResult`
- **平均延迟**: 5ms（轮询间隔的一半）
- **最坏延迟**: 10ms

### 2. CPU 资源浪费
- 即使没有请求，定时器也在持续运行
- 频繁的空轮询消耗 CPU 资源
- 每 10ms 执行一次检查，每秒 100 次

### 3. 网络开销
- 每个轮询都需要建立 HTTP 连接
- 即使没有数据，也要发送请求和响应
- 多个轮询同时进行，增加网络负担

## 优化方案

### 方案 1: 长轮询 (Long Polling) ⭐ 推荐
**优点**:
- 实现简单，改动小
- 延迟低（接近实时）
- 减少空轮询
- 兼容现有 HTTP 架构

**实现**:
- 客户端发起请求后，服务器保持连接打开
- 有数据时立即返回，无数据时等待（最多 1-2 秒）
- 超时后客户端重新发起请求

**预期效果**:
- 延迟: 10ms → <1ms
- CPU 使用: 减少 80-90%
- 网络请求: 减少 90%+

### 方案 2: WebSocket
**优点**:
- 真正的双向实时通信
- 延迟最低
- 连接复用，开销小

**缺点**:
- 需要较大改动
- 需要处理连接管理、重连等

### 方案 3: Server-Sent Events (SSE)
**优点**:
- 单向推送，适合部分场景
- 实现相对简单

**缺点**:
- 只支持服务器到客户端推送
- 仍需要 HTTP 请求做客户端到服务器通信

### 方案 4: 自适应轮询间隔
**优点**:
- 实现简单
- 根据负载动态调整

**缺点**:
- 仍然有延迟
- 无法完全消除空轮询

## 推荐实施计划

### 阶段 1: 长轮询优化（立即实施）
1. 修改 `/pollCallKotlinMethod` 支持长轮询
2. 修改 `/pollCallNativeResult` 支持长轮询
3. 移除 Mac 端定时器，改用事件驱动

**预期收益**: 延迟降低 90%，CPU 使用降低 80%

### 阶段 2: WebSocket 升级（可选）
如果长轮询仍不满足需求，考虑升级到 WebSocket

## 实施细节

### 长轮询实现要点

1. **超时设置**: 1-2 秒
2. **连接保持**: 使用 `NWConnection` 保持连接
3. **立即响应**: 有数据时立即返回，不等待超时
4. **优雅降级**: 如果长轮询失败，回退到短轮询

### 代码改动点

1. `PreviewHttpServer.handlePollCallKotlinMethod()` - 支持长轮询
2. `PreviewHttpServer.handlePollCallNativeResult()` - 支持长轮询
3. `PreviewRenderCoreManager.startCallNativePolling()` - 改为事件驱动
4. JVM 端轮询逻辑 - 支持长轮询超时
